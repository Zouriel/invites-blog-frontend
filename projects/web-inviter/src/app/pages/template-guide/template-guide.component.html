What a template is

A template is one HTML file: your markup, your CSS in a <style> tag and, if you want it, your JavaScript in a <script> tag. Everything lives in that one file.

You mark the spots that change from one invitation to the next with small data-* attributes. When a guest opens their invitation, the platform fills those spots with the event’s details and that guest’s own name, then shows them the finished page.

Your tags build the editor. The inviter only sees the fields your template asks for. Add data-var="event.hashtag" and a “Hashtag” box appears in the builder. Add <img data-src="…"> and an upload slot appears. You don’t write any other code.

If you don’t set a type, the builder guesses from the last part of the path:

  • contains date: a date picker
  • contains time: a time picker
  • contains description, schedule, note, message, story or address: a multi-line box
  • a data-href, or contains link or url: a link box
  • anything else: a one-line box

data-options takes a comma list (Formal,Casual,Black Tie) or a JSON array (["Formal","Casual"]).

Galleries

A plain <img data-src> holds one photo. Add data-multiple="true" and it holds several. The platform copies your <img> once per photo, so every copy keeps your classes and styling. Using the same path on several elements asks the inviter once and fills every element with it.

The paths you can use

{{ d.term }}
{{ d.text }}

  • event.title, event.date and event.time fall back to the event’s own name, date and time when the inviter leaves them blank.
  • guest.role is the guest’s first role. guest.roles is the full list, which is useful in JavaScript.
  • rsvp.label is the right button wording for this guest: “Reply now”, “Confirm your reply” or “Change your reply”. Guests who already said they’re coming get no link and an empty label, so wrap the button in data-optional.
  • camera.link opens the event camera. It only has a value on the event day, and only for guests who said they’re coming. Wrap it in data-optional too.
  • photos.link opens the event’s shared photos.

How filling works

  • A missing value blanks the element. The text you write between the tags shows only until the data is applied. It isn’t a fallback, so test with fields left empty.
  • Wrap anything that can be empty in data-optional, so a blank value removes its label too.
  • A data-href with no value is hidden when its own href is empty or #, so an empty button never jumps the reader to the top.
  • Guest text goes in as text, never as HTML.

Roles

An invitation can have roles: the bride’s side and the groom’s side, bridesmaids, VIPs, family. Sections only some guests see

{{ blockExample }}

On the Roles step, the inviter ticks which blocks each role sees. Then:

  • A block that no role ticked is shown to everyone.
  • A block that any role ticked is shown only to guests with one of those roles.

So put content everyone needs outside any block, or in a block nobody ticks. Block names are up to you; common ones are bridesmaidInstructions, maleDressCode, vipSchedule and familyNote.

Dress colours

The inviter can give each role a palette of up to six colours. Put an empty data-dress-colors element where you want the swatches, and style the classes the platform fills it with. 

{{ dressExample }}
  • The element is hidden when the guest has no colours.
  • Each swatch only gets background inline. Its size and shape are up to you.

If your template has no data-dress-colors, the platform adds its own “Dress colours” section near the end of the invitation.

Theming

Declare your palette as CSS custom properties named --ib-… in :root. Each one becomes a control on the inviter’s Theming step, filled in with your value. Use the variables everywhere instead of fixed colours.

  • Any other --ib-* shows up too: --ib-heading-font is saved as headingFont.
  • A value that starts like a colour gets a colour picker, a name containing font gets a font control, and anything else gets a text box.
  • The first declaration wins, so write your defaults in :root before any @media override. The inviter’s choices are set inline on <html>, so they beat your defaults.
  • The platform also sets --ib-progress on <html>: 0 at the top of the page, 1 at the bottom. Use it to scrub an animation in plain CSS.

Motion and JavaScript

Templates can use CSS, JavaScript or both. Motion is the whole product, so write the animation you actually want. The built-in hooks need no code: data-reveal gets is-visible, data-envelope gets is-open, and --ib-progress tracks the scroll. 

{{ animationExample }}

Prefer CSS scroll-driven animation to a scroll handler. If the motion follows the scroll, animation-timeline runs off the main thread, while a requestAnimationFrame handler competes for it every frame. Reading layout in a scroll handler (getBoundingClientRect(), offsetTop) makes the browser work out the whole page first. Read it once, keep it, and recompute on resize, not on scroll.

Where your template runs

  • Guests get one finished page, filled on the server before it reaches them, and not inside a frame.
  • The builder preview and the gallery run your template inside a sandboxed frame. There the data is applied again on every edit the inviter makes.

Write for both. The common mistakes below show what that means.

The manifest

You never write the manifest by hand. When a template is uploaded, the platform reads your tags and saves a manifest.json next to it. The builder, the Roles step and the Theming step are all built from it.

@for (d of manifest; track d.term) {
{{ d.term }}
{{ d.text }}
}

The Check button on the submission form shows what was detected. It’s the quickest way to confirm your tags are right.

Versions are frozen. Every invitation keeps the exact package and manifest it was created with. An edit publishes a new version and never changes invitations that already exist.

Packaging and submitting

  • One self-contained file. Inline your CSS and JavaScript. <link rel="stylesheet"> and <script src="…"> are rejected, because what a reviewer approves has to be what actually runs.
  • Embed images and fonts as data: URIs. The guest page only loads images and fonts from invites.blog itself or from data: URIs, and blocks network requests and forms. An image or font linked from another site won’t show for guests.
  • Keep it light. Aim for under 300 KB, where the Check starts warning you. 800 KB is the hard limit.
  • It runs sandboxed. Your page can’t read cookies, localStorage or the app’s session. Links with target="_blank" still open.

Common mistakes

  • Cloning elements on every data pass. In the builder preview the data is applied again on every edit. If your script clones or generates elements, mark what you made and clear it before making it again. Otherwise a gallery of six photos becomes thirty-six, then two hundred and sixteen.
  • Treating placeholder text as a fallback. A missing value blanks the element. Your placeholder only shows before the data arrives.
  • Per-child CSS variables with no default. Number children :nth-child(1..6) and feed that into an animation-range, and a seventh child animates across the whole timeline. Set a default on the base rule.
  • Too many animations that never stop. Dozens of always-moving decorations can cost more each frame than several full-size photos.
  • Designing for full-size photos. Gallery images are resized to 512 px on the long edge.
  • A scroll track built from viewport units. vh and dvh change when the phone’s address bar moves, and inside the preview frame. Tie ranges to the element instead.
  • Relying on reduced motion. The platform removes @media (prefers-reduced-motion: reduce) rules, because an invitation without motion is broken.
  • Linking fonts or images from another site. They may work in the preview and then fail for guests. Embed them.
  • Putting everything in blocks. A block any role ticked is hidden from everyone else, so a guest with no matching role gets a half-empty invitation.
