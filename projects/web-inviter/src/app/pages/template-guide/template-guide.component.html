For creators Making a template A template is one HTML file — your markup, with your CSS in a <style> tag. You mark the spots that should be filled in with small data-* tags, and the platform fills them with the event’s details and each guest’s own information inside a sandboxed frame.

The builder is driven by your template. It shows the inviter exactly the fields your template declares — no more, no less. Add a data-var for event.hashtag and a "Hashtag" box appears in the builder by itself. Add an <img data-src> and an upload slot appears. You never touch any other code. The tags Optional hints The builder works without these, but they polish the inviter’s experience. Input kinds Set none and the builder guesses well: paths containing date get a date picker, time a time picker, description / schedule / note / message / address a multi-line box, links a URL box, everything else a normal text box. data-options takes a comma list or a JSON array. Who fills what
  • The inviter fills any event.* path and its images — event.title, event.date, event.dressCode, event.coverImage, and anything else you invent.
  • Personal to each guest, added automatically — guest.name, guest.role, guest.gender. Don’t expect anyone to type these.
  • Generated by the platform — rsvp.link, rsvp.status, invite.link.
  • Filled in their own steps — event.venue.* (Venue) and inviter.* (Inviter). Use them freely; they’re filled elsewhere.

Always write sensible fallback text between the tags — it shows until the real value loads, and whenever a value is left blank. Wrap anything optional in data-optional so an empty value disappears cleanly instead of leaving a dangling label. Theming Declare your palette as CSS custom properties named --ib-… in :root. Each one becomes a real control in the inviter’s Theming step, pre-filled with your default — so they can recolour your template without you writing anything extra. Use the variables everywhere instead of hardcoding colours. The first declaration wins, so put your defaults in :root before any @media override. Any other --ib-* shows up too — --ib-heading-font becomes headingFont. A value that looks like a colour gets a colour picker; a name containing font gets a font control; anything else gets a text box.

Roles An invitation can have several roles — bride’s side and groom’s side, VIPs, family. The inviter names them in the wizard’s first step, then themes and fills each one. Anything without data-role-scope is shared and filled once; anything with it belongs to that role alone. Every role can override every --ib-* key, so a bride’s side in blush and a groom’s side in navy costs you nothing. 
{{ rolesExample }}
data-role-scope is about who fills what. data-block is about who sees what when it’s sent. They’re complementary — use both. Role-based content Put data-block="someId" on a section. Whether a guest sees it is decided by the roles the inviter set up, which map a guest’s role to block ids. A block no rule mentions is shown to everyone — so put universal content in unmentioned blocks, and every guest still gets a complete invitation. Animation — CSS only Every upload is scanned, and any <script>, inline onclick= or onload= handler, javascript: URL or meta refresh is rejected outright — for every author, admins included. Nothing is silently stripped: you get a clear error naming what to remove. You don’t need JavaScript for motion. data-reveal gets is-visible when it scrolls into view, and data-envelope gets is-open after the first scroll. The whole invitation is scroll-driven, so CSS on those two classes covers cover reveals, fades, staggered entrances and envelope openings.

The rules
  • One self-contained file. Inline your CSS and embed images as data: URIs. An external stylesheet is rejected.
  • No JavaScript — use CSS with the two classes above.
  • Keep it light — aim under 300 KB. 800 KB is a hard limit and anything over it is rejected.
  • Respect reduced motion with a @media (prefers-reduced-motion: reduce) block.
  • Guest text is inserted as text, never markup — safe by design.
 Submitting it Submit from Start a template with two files: index.html, and a preview.png — required, it’s the card art guests and hosts see.
  1. The automatic scan runs immediately. Scripts, inline handlers, javascript: URLs, meta refresh, an external stylesheet, anything over 800 KB, or a select with no data-options are rejected on the spot — nothing reaches a human. The Check button dry-runs it and shows every field, image slot, role and theme key detected.
  2. It enters the review queue. An admin sees your markup and a plain-language summary of what it declares, then approves it or rejects it with a reason you’ll see on your submissions list.
  3. On approval it’s published at version 1.0.0.
Editing a published template works the same way — submit the change and it goes through review again. Approval bumps the version, and the old version stays exactly as it was, so invitations already built on it never change. A starter, in one file
