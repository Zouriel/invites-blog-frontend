1. What a template is A template is one HTML file: your markup, your CSS in a <style> tag and, if you want it, your JavaScript in a <script> tag. Everything lives in that one file. You mark the spots that change from one invitation to the next with small data-* attributes. When a guest opens their invitation, the platform fills those spots with the event’s details and that guest’s own name, then sends them the finished page. The inviter only sees the fields your template asks for. Add data-var="event.hashtag" and a “Hashtag” box appears in the builder. Add <img data-src="…"> and an upload slot appears. You don’t write any other code. 2. A minimal working example Copy this, open it in a browser, then change it.

They make it nicer for the inviter. data-field-type is the old name for data-type and still works; if an element has both, data-type wins. Input kinds If you don’t set a type, the builder guesses from the last part of the path:
  • contains date → date picker
  • contains time → time picker
  • contains description, schedule, note, message, story or address → multi-line box
  • a data-href, or contains link or url → link box
  • anything else → one-line box
data-options takes a comma list (Formal,Casual,Black Tie) or a JSON array (["Formal","Casual"]). Galleries A plain <img data-src> holds one photo. Add data-multiple="true" and it holds several. The platform copies your <img> once per photo, so every copy keeps your classes and styling. Using the same path on several elements asks the inviter once and fills every element with it.

The paths you can use
  • event.title, event.date and event.time fall back to the event’s own name, date and time when the inviter leaves them blank.
  • guest.role is the guest’s first role. guest.roles is the full list, which is useful in JavaScript.
  • rsvp.label is the right button wording for this guest: “Reply now”, “Confirm your reply” or “Change your reply”. Guests who already said they’re coming get no link and an empty label, so wrap the button in data-optional.
  • camera.link opens the event camera. It only has a value on the event day, and only for guests who said they’re coming. Wrap it in data-optional too.
  • photos.link opens the shared photo gallery.
How filling works
  • A missing value blanks the element. The text you write between the tags shows only until the data is applied. It is not a fallback. Test with fields left empty.
  • Wrap anything that can be empty in data-optional, so a blank value removes its label too.
  • A data-href with no value is hidden if its own href is empty or #, so an empty button never jumps the reader to the top.
  • Guest text goes in as text, never as HTML.
 4. Roles An invitation can have roles: the bride’s side and the groom’s side, bridesmaids, VIPs, family. The inviter names them on the Roles step. Then they choose which of your sections each role sees, and optionally a dress colour palette per role. Roles do three different jobs, each with its own attribute: Declaring roles List the roles your template has in mind with a meta tag. Any role named in a data-role-scope counts as declared too. The Roles step suggests these names. Role names are turned into lowercase slugs, so Bride & Groom becomes bride-groom.

Each role can also have its own value for every --ib-* theme colour, so a bride’s side in blush and a groom’s side in navy needs no extra work from you. Sections only some guests see 
{{ blockExample }}
On the Roles step, the inviter ticks which blocks each role sees. Then:
  • A block that no role ticked is shown to everyone.
  • A block that any role ticked is shown only to guests with one of those roles.
So put content everyone needs outside any block, or in a block nobody ticks. Block names are up to you; common ones are bridesmaidInstructions, maleDressCode, vipSchedule and familyNote. Theming Declare your palette as CSS custom properties named --ib-… in :root. Each one becomes a control on the inviter’s Theming step, pre-filled with your value. Use the variables everywhere instead of fixed colours. 
{{ themeExample }}
Every template should declare these three:
  • Any other --ib-* shows up too: --ib-heading-font is saved as headingFont.
  • A value that starts like a colour gets a colour picker; a name containing font gets a font control; anything else gets a text box.
  • The first declaration wins, so write your defaults in :root before any @media override. The inviter’s choices are set inline on <html>, so they beat your defaults.
  • The platform also sets --ib-progress on <html>: 0 at the top of the page, 1 at the bottom. Use it to scrub an animation in plain CSS.
6. Motion and JavaScript Templates can use CSS, JavaScript, or both. Motion is the whole product, so write the animation you actually want. You need no code for the built-in hooks: data-reveal gets is-visible, data-envelope gets is-open, and --ib-progress tracks the scroll. 
{{ animationExample }}
If the motion follows the scroll, animation-timeline runs on the compositor, while a requestAnimationFrame handler competes for the main thread every frame. Reading layout in a scroll handler (getBoundingClientRect(), offsetTop) makes the browser work out the whole page first. Read it once, cache it, and recompute on resize, not on scroll. Where your template runs
  • Guests get one finished page, filled on the server before it was sent, and not inside a frame.
  • The builder preview and the gallery run your template inside a sandboxed frame. There the data is applied again on every edit the inviter makes.
Write for both. See the common mistakes below for what that means. 7. The manifest You never write the manifest by hand. When a template is uploaded, the platform reads your tags and saves a manifest.json next to it. The builder, the Roles step and the Theming step are all built from it. The Check button on the submission form shows what was detected. It’s the quickest way to confirm your tags are right. Every invitation keeps the exact package and manifest it was created with. An edit publishes a new version and never changes invitations that already exist. 8. Packaging and uploading
  • One self-contained file. Inline your CSS and JavaScript. <link rel="stylesheet"> and <script src="…"> are rejected: what a reviewer approves has to be what actually runs.
  • Embed images and fonts as data: URIs. The guest page only loads images and fonts from the platform itself or from data: URIs, and blocks network requests and forms. An image or web font linked from another site won’t show for guests.
  • Keep it light. Aim for under 300 KB, where the Check starts warning you. 800 KB is a hard limit.
  • Sandboxed. Your page can’t read cookies, localStorage or the app’s session. Links with target="_blank" still open.
Submitting as a designer Submit from Start a template with two files: your index.html, and a preview image. The image is required; it’s the card people see in the gallery.
  1. The automatic check runs straight away. It rejects an external stylesheet or <script src>, a file over 800 KB, and a select with no valid data-options. Press Check first to try it without submitting.
  2. A person reviews it. A reviewer reads your markup and approves it, or rejects it with a reason you’ll see on your submissions list. Nobody approves their own work.
  3. On approval it’s published in the gallery at version 1.0.0.
To change a published template, submit the change. It goes through review again, approval bumps the version, and the old version stays exactly as it was. Common mistakes
  • Cloning elements on every data pass. In the builder preview the data is applied again on every edit. If your script clones or generates elements, tag what you made and clear it before making it again. We once shipped a gallery that turned six photos into thirty-six, then two hundred and sixteen.
  • Treating placeholder text as a fallback. A missing value blanks the element. Your placeholder only shows before the data arrives.
  • Per-child CSS variables with no default. Number children :nth-child(1..6) and feed that into an animation-range, and a seventh child animates across the whole timeline. Set a default on the base rule.
  • Too many animations that run forever. One template had 56 always-moving decorations costing about 4 ms a frame, more than six full-size photos.
  • Designing for full-size photos. Gallery images are resized to 512 px on the long edge.
  • A scroll track built from viewport units. vh and dvh change when the phone’s address bar moves, and inside the preview frame. Tie ranges to the element instead.
  • Relying on reduced motion. The platform removes @media (prefers-reduced-motion: reduce) rules, because an invitation without motion is broken.
  • Linking fonts or images from another site. They may work in the preview and then fail for guests. Embed them.
  • Putting everything in blocks. A block any role ticked is hidden from everyone else, so a guest with no matching role gets a half-empty invitation.
