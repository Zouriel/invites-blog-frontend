For creators Making a template A template is one HTML file — your markup, with your CSS in a <style> tag. You mark the spots that should be filled in with small data-* tags, and the platform fills them with the event’s details and each guest’s own information inside a sandboxed frame.

The builder is driven by your template. It shows the inviter exactly the fields your template declares — no more, no less. Add a data-var for event.hashtag and a "Hashtag" box appears in the builder by itself. Add an <img data-src> and an upload slot appears. You never touch any other code. The tags Optional hints The builder works without these, but they polish the inviter’s experience. Input kinds Set none and the builder guesses well: paths containing date get a date picker, time a time picker, description / schedule / note / message / address a multi-line box, links a URL box, everything else a normal text box. data-options takes a comma list or a JSON array. Who fills what
  • The inviter fills any event.* path and its images — event.title, event.date, event.dressCode, event.coverImage, and anything else you invent.
  • Personal to each guest, added automatically — guest.name, guest.role, guest.gender. Don’t expect anyone to type these.
  • Generated by the platform — rsvp.link, rsvp.status, invite.link.
  • Filled in their own steps — event.venue.* (Venue) and inviter.* (Inviter). Use them freely; they’re filled elsewhere.

Always write sensible fallback text between the tags — it shows until the real value loads, and whenever a value is left blank. Wrap anything optional in data-optional so an empty value disappears cleanly instead of leaving a dangling label. Theming Declare your palette as CSS custom properties named --ib-… in :root. Each one becomes a real control in the inviter’s Theming step, pre-filled with your default — so they can recolour your template without you writing anything extra. Use the variables everywhere instead of hardcoding colours. The first declaration wins, so put your defaults in :root before any @media override. Any other --ib-* shows up too — --ib-heading-font becomes headingFont. A value that looks like a colour gets a colour picker; a name containing font gets a font control; anything else gets a text box.

Roles An invitation can have several roles — bride’s side and groom’s side, VIPs, family. The inviter names them in the wizard’s first step, then themes and fills each one. Anything without data-role-scope is shared and filled once; anything with it belongs to that role alone. Every role can override every --ib-* key, so a bride’s side in blush and a groom’s side in navy costs you nothing. 
{{ rolesExample }}
data-role-scope is about who fills what. data-block is about who sees what when it’s sent. They’re complementary — use both. Role-based content Put data-block="someId" on a section. Whether a guest sees it is decided by the roles the inviter set up, which map a guest’s role to block ids. A block no rule mentions is shown to everyone — so put universal content in unmentioned blocks, and every guest still gets a complete invitation. Animation Motion is the whole product here, so nothing stops you writing the animation you actually want. Your script has to be inline in the file — <script src="…"> is rejected, because what a reviewer approves has to be what actually runs. Everything renders in a sandboxed frame with an opaque origin, so a template can’t reach the app around it. You still don’t need JavaScript for motion. data-reveal gets is-visible when it scrolls into view, and data-envelope gets is-open after the first scroll. If the motion follows the scroll, animation-timeline runs on the compositor, while a requestAnimationFrame handler competes for the main thread every frame. And a layout read inside a scroll handler — getBoundingClientRect(), offsetTop — forces the browser to resolve layout for the whole document before it can answer. Read geometry once and cache it; recompute on resize, not on scroll.

The rules
  • One self-contained file. Inline your CSS and your JavaScript, and embed images as data: URIs. An external stylesheet or <script src="…"> is rejected — a file fetched from somewhere else can become something else the day after it was approved.
  • A person reads your template. There’s no automatic scan for scripts any more; a reviewer reads the markup before it can reach anyone.
  • Ship a poster.webp — the gallery shows that still, not your live template. Portrait, about 720×1280, captured with sample copy filled in.
  • Keep it light — aim under 300 KB. 800 KB is a hard limit and anything over it is rejected.
  • Don’t rely on reduced motion. An invitation’s whole value is its motion, so the platform strips @media (prefers-reduced-motion: reduce) rules at runtime. If you want a calmer variant, key it off something you control.
  • Guest text is inserted as text, never markup — safe by design.
 We intend to move the guest-facing invitation off the iframe and render it on the server as a normal page on its own origin — one document, filled in before it’s sent. That would remove two of the traps below and make a guest’s first paint much faster. It’s a direction, not a promise, and nothing changes until it ships. Previews inside the signed-in app keep the sandboxed frame either way. Write to the contract on this page and your template works under both. Things that have bitten us All of these came out of real breakage. Worth ten minutes before you ship.
  • Your data is applied more than once. The platform binds on load, and again every time fresh data arrives — the builder sends it on every edit. If your script clones or generates elements, make it idempotent: tag what you created and clear it before creating it again. We once shipped a binder that cloned a gallery on each pass, so six photos became thirty-six. It looked exactly like an animation bug.
  • Anything you don’t supply is blanked. Binding sets an element’s text to empty when there’s no value for it. Your placeholder text shows before data arrives — it is not a fallback afterwards. Test with fields missing.
  • Give per-child CSS variables a default. If you number children :nth-child(1..6) and feed that into an animation-range, a seventh child gets an undefined variable, the range falls back to the entire timeline, and that element animates across the whole section. With several extra children all doing it at once, it flickers.
  • Count the things that animate forever. One template had 56 continuously animating decorations costing ~4 ms a frame — more than six full-resolution photographs did. Infinite animations aren’t free just because they’re small.
  • Photos are smaller than you think. Gallery images are capped at 512 px on the long edge, because six full-size photos is tens of megabytes of decoded bitmap. Design prints to be small.
  • Don’t build a scroll track out of viewport units. Anything sized in vh/dvh is relative to the frame, and the frame can be resized by the browser’s own chrome mid-scroll — which remaps the reader into a different part of your animation. Prefer ranges tied to the element.
Submitting it Submit from Start a template with two files: index.html, and a preview.png — required, it’s the card art guests and hosts see.
  1. The automatic scan runs immediately. It checks that the file is self-contained (no external stylesheet or <script src>), that it is under 800 KB, and that a select declares its data-options. It no longer looks for JavaScript. The Check button dry-runs it and shows every field, image slot, role and theme key detected.
  2. It enters the review queue. An admin sees your markup and a plain-language summary of what it declares, then approves it or rejects it with a reason you’ll see on your submissions list.
  3. On approval it’s published at version 1.0.0.
